## 优化方法论

本工具综合以下业界公认的提示词优化框架：

### 1. CO-STAR 框架

CO-STAR 是一个结构化提示词框架，确保提示词包含所有关键要素：

- **C (Context)**: 背景信息 - 提供任务的上下文
- **O (Objective)**: 目标 - 明确要完成什么
- **S (Style)**: 风格 - 指定输出的语气和风格
- **T (Tone)**: 语气 - 设定回复的情感色彩
- **A (Audience)**: 受众 - 说明目标读者是谁
- **R (Response)**: 响应格式 - 定义期望的输出结构

**应用场景**: 从零开始构建新提示词，或重构模糊不清的提示词

### 2. Chain-of-Thought (CoT)

思维链提示技术，引导 AI 逐步推理：

- **基础 CoT**: 在提示词中添加"让我们一步步思考"
- **Few-Shot CoT**: 提供带推理过程的示例
- **Zero-Shot CoT**: 无需示例，直接触发推理

**应用场景**: 复杂推理任务、数学问题、多步骤分析

### 3. ACON 两阶段优化

基于 arXiv:2510.00615 论文：

**阶段1 - 关键信号提取**:
- 角色定义 (Role)
- 任务目标 (Task)
- 约束条件 (Constraints)  
- 输出格式 (Format)
- 成功标准 (Success Criteria)

**阶段2 - 选择性压缩**:
- 只删除冗余，保留所有关键信号
- 根据 λ 参数控制压缩程度（0.2-0.8）
- 功能等价性验证

**应用场景**: 长提示词压缩，在保持效果的前提下降低 token 成本

### 4. APE 自动提示工程

基于 arXiv:2211.01910 论文：

- 生成多个候选提示词（不同风格）
- 按清晰度、完整性、有效性打分
- 选择最优候选

**应用场景**: 探索多种表达方式，找到最有效的提示词

### 5. Self-Refine 自我优化

迭代优化循环：

1. 生成初始输出
2. 自我评估找出不足
3. 基于反馈改进
4. 重复直到满意

**应用场景**: 需要多轮打磨的创意内容、技术文档

## 使用方式

### 标准优化流程

当用户提供原始提示词时，执行以下步骤：

**Step 1: 意图识别**
- 分析提示词类型（知识查询/创意生成/代码任务/分析任务）
- 识别当前缺失的要素
- 判断是否需要压缩（token 数 > 1000）

**Step 2: 选择优化策略**
- 结构缺失 → 应用 CO-STAR 框架
- 需要推理 → 引入 Chain-of-Thought
- 提示词过长 → 应用 ACON 压缩
- 效果不确定 → 尝试 APE 生成候选

**Step 3: 生成优化版本**
- 保留原始意图和所有关键信号
- 补充缺失要素
- 优化表达清晰度
- 输出用代码块包裹，方便复制

**Step 4: 主动收集反馈**

输出优化后，询问用户：

> 已完成优化。是否满意？如有不满意（效果不够好/还是太长/某些要求没保留/其他），请告诉我，我会继续迭代。
>
> *(English)* Optimization complete. Satisfied? Let me know if anything needs adjustment and I'll iterate.

**Step 5: 迭代优化**

根据用户反馈调整：
- 效果不好 → 补充更多约束和示例
- 还是太长 → 增加压缩力度（提高 λ）
- 内容缺失 → 补回关键信号
- 其他要求 → 针对性调整

重复直到用户满意。

## 优化原则

### ✅ 必须遵守

1. **保留所有关键信号**: 角色、目标、约束、格式、示例、变量占位符
2. **功能等价**: 优化后的提示词必须产生与原提示词相同质量的输出
3. **先效用后压缩**: 优先提升清晰度和完整性，再考虑压缩
4. **验证每一步**: 每次修改后验证关键信号是否完整

### ❌ 禁止操作

1. **不自动触发**: 只在用户明确要求时工作
2. **不删除关键信号**: 角色定义、约束条件、输出格式等永不删除
3. **不主观评价**: 基于框架方法论，不凭主观印象
4. **不输出对比分析**: 只输出优化结果，除非用户要求

## 方法论选择指南

| 场景 | 推荐方法 | 原因 |
|------|---------|------|
| 模糊的单句提示词 | CO-STAR | 补全结构化要素 |
| 数学/逻辑推理任务 | Chain-of-Thought | 引导逐步推理 |
| 长提示词（>1000 token） | ACON | 压缩冗余，保留核心 |
| 不确定最佳表达 | APE | 生成多个候选，选优 |
| 创意内容打磨 | Self-Refine | 多轮迭代改进 |
| 结构完整但表达冗余 | ACON 压缩 | 精简表达，保持功能 |

```
**Context**: 你是一位资深科技博客作者，擅长用通俗易懂的语言解释复杂技术概念

**Objective**: 撰写一篇 800-1000 字的技术博客文章

**Style**: 专业但不失亲和力，适合技术爱好者阅读

**Tone**: 友好、启发性、充满洞察

**Audience**: 对技术感兴趣但非专业开发者的读者

**Response**: 文章结构应包含：
1. 引人入胜的开头（100字）
2. 核心概念解释（400字）
3. 实际应用案例（300字）
4. 总结与展望（200字）
```
